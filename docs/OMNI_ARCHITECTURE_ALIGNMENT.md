- 保留当前 React / FastAPI / Python / SQLite 技术栈。参考文档第12节的 TypeScript 路径是另一套工程的规划位置，不据此搬迁当前项目或重写已有业务。

## 改造顺序

1. **证据与覆盖门禁**：先落规则来源、逐条状态、缺证据降级、时间范围、模态一致性、缺失型覆盖条件，使用离线测试证明这些系统不变量。此前已做的JSON协议、原始响应留存和分层错误继续保留。
2. **输入与工具协议**：再落实能力配置、可达的受控临时URL、分段、精听/精看和证据登记。未配置可达存储/网关时明确不可用，不静默回退到不符合约束的长片Base64方案，也不自动上传用户视频到外部服务。
3. **四阶段编排**：实现建图、代码立案、局部精查、代码汇总。以窗口共享缓存减少重复看/听，以每规则finding保证判定覆盖；模型不得决定跳过规则或自行结束整个审核。
4. **人审与交付**：按严重度和待人工原因组织复核队列、播放器时间轴、申诉说明与证据包。服务端验证后才计算评分或发布建议。
5. **实测与评测**：在用户显式确认的真实调用预算内验证模型/网关/音轨能力与成本；然后开展人工标注参照的分层质量评测。格式成功率和判断质量分别统计。

## 落地时需明确的语义

- `unverifiable`作为判定/可验证状态，保留规则本身的严重度，避免把严重度与证据不足混成一个字段。具体对外枚举变更须有兼容迁移。
- L2的品牌要求必须回引Brief原文；L0/L1应回引核实过的法规/平台规则及版本，人工规则应标明品牌确认来源，不能伪造为Brief出处。没有来源的新增要求不得被模型自行升级为否决项。
- 全片转写上的确定性词表匹配只证明算法可复现；转写覆盖不足、识别不确定时，不能据此断言全片缺少某词或台词违规。
- 局部任务可按共享窗口执行并关联多个规则，最终结论仍逐规则保存。局部预算和共享缓存不能导致某条规则没有结果。
- 长片的Phase A按分段建图后合并；“1次通看”的短片示例不能解释为长片也必须只调用一次。
- 参考文档第13节尚未定论的参数继续保留为待实测项，特别是视频投喂方式、hints策略、全局预算和听觉严重度；不把示例数字直接升级为已验证生产配置。
